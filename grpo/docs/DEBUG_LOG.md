# 开发、数值与验证记录

## 原主线的限制

原 RLTrain 主要由 8×4090 的 veRL/并行框架编排与诊断组成，完整实现仍有学习价值，但资源要求和通信拓扑限制了本轮复现。原高层配置对照的实际 token 数不同，也不能把 2.13× 当成单一自写模块的收益。新版单卡损失模块与这些旧数字分开。

## 按 token 分块并不够

最初每个 token 块都重建并累加大词表权重梯度，临时 FP32 `V×D` 缓冲和重复读写成为负担。开发测量明显慢于 torch.compile。保留这个实现作为 sequence 对照，改为按词表遍历：直接写出每块 dW，累加小得多的 `N×D` hidden 梯度。之后还把输出 GEMM 直接写到目标切片，避免额外 dW 临时分配及复制。

这是根据负面结果改变实现，而不是只调 chunk 参数；正式消融使用同一源码和相同输入散列重跑两种遍历。

## 数据准备和全零优势

Transformers 5.19 的 chat-template 调用默认返回 BatchEncoding，最初准备脚本把它当 token ID 列表，JSON 序列化失败。改为显式 `return_dict=False` 并检查扁平整数列表。

第一批 4 题×4 响应、128-token 的真实采样全部截断，正确性奖励全零，长度也相同，优势全零。它没有作为训练成功证据。使用相同题目和预先定义奖励，将整批生成预算扩至 256；有效响应 3830 token、16 个非零优势。正确性项仍全零，非零信号来自长度项。数据保留用于系统计算验证，不解释为数学能力学习成功。

## 优化器更新验证不能只看最终权重

早期检查比较最终参数向量的相对误差；预训练权重远大于几步小更新，这样即使优化器不更新也可能“很接近”。修正为先保存初值、再直接比较 `最终值-初值` 的更新向量，并检查所有参数集合和非零更新。

加强后的第一版真实 BF16 检查失败：eager 与 torch.compile 的首步梯度相对 L2 约 0.0134、cosine 约 0.999910，但三步更新相对 L2 约 0.2008、cosine 约 0.979973，未达到预设 0.1 / 0.995 阈值。该失败及原源码快照保留在 development。

没有放宽这组原阈值以宣布“参数更新一致”。验证分为：

- FP64 公式、有限差分、三步 Adam 更新是数学实现门槛。
- GPU FP32/BF16 算子及真实模型首步梯度按预定容差检查。
- 真实模型 BF16 三步更新保留原通过/失败状态，作为数值漂移诊断；另外要求实际更新非零，以排除 no-op 优化器。

最终“阶段完成”不代表所有多步漂移阈值都通过。是否超出原阈值在比较 JSON 和最终表中显式显示，不声称 BF16 训练轨迹等价。自定义实现、torch.compile 和 Liger 都必须报告，不只保留对自己有利的一对。

小梯度数值变化可能经 Adam 归一化与后续前向放大，但本轮没有定位到某个具体 kernel 或完整因果分解，不能把全部偏差直接归给 cuBLAS、Triton 或优化器。

## 编译反向的 autocast 契约

本训练代码按 AMP 规范在 autocast 中前向，在外部 backward。PyTorch 文档说明 torch.compile 的默认 `backward_pass_autocast="same_as_forward"` 不一定对应这个模式，因此为编译区域显式选择 `"off"`。这不是自写优化，也没有作为加速贡献。

## 测量中的分离

全量梯度和更新的 CPU 快照检查会拖慢运行，因此独立精度运行的 `timing_usable=false`，不参与训练性能表。模型步性能另起进程、保留同批输入和初始化。首轮包含编译、优化器状态初始化，完整保留，稳态统计从后续三步取中位数。

内核融合微基准计 forward+backward，包含 Liger 在 forward 中预计算的梯度。GPU 高性能计数器没有用于本轮结论，不声称测得带宽饱和率或 occupancy。
